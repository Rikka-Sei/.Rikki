# 受审计的增量交付（Audited Incremental Delivery）

## 何时引入

满足任意两条即可引入：

- 预计产生两个以上可独立验证的增量；
- 下一步依赖上一步的接口、契约或数据；
- 需要 reviewer、审计、测试或真实目标证据；
- worktree 中可能出现“已完成但未提交”；
- 用户说“都做完再看”或要求最后统一评审；
- 用户要求 reviewer 与主代理对抗，或要求把原始需求交给 reviewer；
- 结论涉及性能、容量、稳定性或安全；
- 交付跨越多个提交、分支或 worktree。

不引入：

- 单文件机械改动；
- 无行为变化的纯格式调整；
- 一次性小 bug，已有明确测试且不涉及审计和提交节奏。

## 名称含义

- `audited`：每个完成的增量都有自审和外部审计检查点；
- `incremental`：按可独立验证、可独立提交的小步推进；
- `delivery`：交付可验证的实际改动；提交、合并和推送分别受用户授权约束。

## 版本与变更

`version` 使用 SemVer，并且只描述本 skill，不和 `nLsyntax` 或其他 skill 锁步。

- major：触发条件、流程约束或状态契约发生不兼容变化；
- minor：新增章节、工具、模板或新的检查点；
- patch：只改措辞、示例或错别字，不改变行为。

每次修改 `SKILL.md` 都同时更新 frontmatter 的 `version` 和
`CHANGELOG.md`；获准提交时，提交说明写明版本。引用其他 skill 时记录对方名称，不复制
对方的版本。

## 核心法则

每个增量必须先验证、自审和独立审计，再开始下一个依赖增量。

**实现授权不等于提交授权。** 用户未要求提交时，不创建提交；用户明确禁止提交时，不暂存、不提交。已验证增量用工作区 diff 标识记录范围、证据和未提交原因，继续已授权的实现，不因缺少提交授权停下整个任务。

diff 标识要能定位审计时的固定差异，明确基准、范围和时点，并包含未跟踪文件与删除项；沿用现有审计记录的标识方式即可。不能只写一条会随工作区变化的 `git diff` 命令，也不能遗漏用户原有改动的边界。

下个依赖增量应与上次已审计的差异区分；无法单独分离时，重审相关路径的累计差异并明确覆盖范围，不冒充独立增量。确需保存补丁时，遵守下文项目本地材料的授权和隐私规则，不因此备份整个会话。

已获分阶段提交授权时，每个已验证、已审计增量及时提交，不把工作留到最后统一评审。worktree 隔离、审计和验证不能因是否提交而省略。

## 交付循环

```text
1. 明确契约和非目标。
2. 在分支或 worktree 中隔离；记录用户已有的未提交改动。
3. 建立当前行为或失败基线。
4. 把工作切成可独立审查的增量。
5. 实现一个增量及其测试。
6. 运行针对性验证，记录命令和输出。
7. 自审这个增量。
8. 把具体提交或 diff 标识所对应的固定差异，以及用户原始需求（最小相关原话，或已授权项目本地材料的精确位置）交给相关 reviewer。
9. 记录已审计差异；已获提交授权时，只提交这个已验证增量，否则保留工作区改动。
10. 再开始下一个依赖增量，或整合分支。
```

没有验证和审计结论时，不进入下一个依赖增量。未获提交授权不阻止已授权的实现；授权状态与验证状态分别记录。

## 插入询问与中断

用户中途插入问题时，先处理问题，再处理任务状态。

1. **先直接回答**，不要用流程说明替代答案。
2. **分类**：信息询问、纠正、新约束、授权、仅要求继续。
3. **询问**：回答后回到当前增量；不重做已完成工作，也不改变其状态。
4. **纠正**：先承认并修正行为、代码或规则；把修正落到对应增量或 skill。
5. **新约束**：更新当前增量范围；若影响已完成部分，先审计影响。需要补提交、回滚或删除时分别核对授权，不把纠正当作额外权限。
6. **授权**：只执行明确授权的范围；“无所谓/继续”不等于无限权限，不覆盖原有的安全、提交和清理约束。
7. **事故类询问**：先回答事实和不确定性，再说明防复发动作；不要把“没关系”当成按原方式继续操作的许可。
8. **阻塞**：保留 checkpoint，说明当前状态和下一步，再继续。
9. **不要忽略插入继续原计划，也不要把插入当成取消整个任务。**

## 交付记录表与上下文恢复

第一个增量开始前，用本 skill 的脚本建立或定位当前 worktree 的记录：

```bash
python .claude/skills/audited-incremental-delivery/scripts/rana_workspace.py --plan <plan.md>
# 或没有计划文件时：
python .claude/skills/audited-incremental-delivery/scripts/rana_workspace.py --slug <branch-or-task>
```

路径固定为：

```text
<RānaKaname>/workspaces/<slug>/progress.md
```

`.RānaKaname/` 是仓库根下的本地状态目录；写入前确认已排除版本跟踪和发布打包，不能仅凭目录名或 `.gitignore` 假定安全。每个 worktree 各有一份，同一 worktree 默认只有一个写入者。它不依赖 `.superpowers`，也不把增量记录放进 `.tmp`。

每个增量后更新：

- 当前契约、非目标、worktree/branch、base commit；
- 用户原始需求及本增量覆盖范围；
- 已完成的增量、提交、验证命令和 reviewer 结论；
- diff 标识所对应的改动范围，以及事先约定的必测指标、验收阈值和波动上限；
- 插入询问及其决策、恢复点；
- 仍未验证、被阻塞或已过期的证据。

默认只记录最小必要摘要，不另行复制原始会话。确需日志或 benchmark 原始输出时，只将已授权、已检查敏感内容的材料放在项目本地记录旁的 `artifacts/`，记录用途和保留期限；不得写入 skill 目录。任务结束或到期后，按用户授权清理材料，保留不含隐私的结论。

上下文压缩、会话重启或换 agent 时：

1. 先读当前项目的 `progress.md`、授权范围和证据位置；从实际工作区核对分支、改动及运行对象，不依赖 skill 内的会话附件；
2. 不凭记忆重建状态，也不恢复已被用户删除的材料；
3. 在当前代码与运行对象上重跑相关验证；代码、环境或审计标准已变时，旧结论不能直接沿用；
4. 更新 `progress.md` 后再继续。

`progress.md` 不是提交日志的替代品；它记录“为什么现在停在这里、下一步是什么”。

## 什么算一个增量

一个增量是最小单元，满足：

- 只改一个契约或一个行为；
- 能用一条提交说明讲清；
- 有测试或明确的验证命令；
- 不需要读完整计划就能审查；
- 回滚时不会带走无关工作。

相互依赖的规格、测试、manifest 和代码放在同一个增量里。“整个计划”不是增量。

如果暂时无法切分，要说明具体依赖并先征询，不能默默把全部工作做成一个大提交。

## 审计检查点

审计是循环的一部分，不是最后一道仪式。

### 请求别人之前的自审

逐项检查并记录：

- 增量是否符合约定和非目标；
- 验证是否覆盖新行为及有意义的失败边界；不为措辞、转发或源文本新增永久测试；
- 工作区与暂存区是否混入用户改动、生成物或无关 diff；未跟踪文件与删除项是否纳入审计范围；
- 资源生命周期：键是否有界、创建/删除是否配对、失败和关闭是否清理；
- 性能结论是否使用了正确的证据等级；
- 术语可读性：按 nLsyntax 检查报告、提交说明和 skill/规则文档；
- 对抗性审计请求是否包含用户原始需求；reviewer 就原始需求提出的问题是否已有文件、行号、命令或提交哈希证据回答并记录；
- 交付记录是否写明实际跑过的命令、被阻塞的检查和提交授权状态。

### 下一个依赖增量之前的外部审计

给 reviewer 具体的提交哈希或 diff，不要只给摘要。要求返回：

- 阻断性的正确性/安全问题；
- 证据缺口和无效对比；
- 缺失的反例；
- 明确的 approve/changes 结论。

reviewer 的任务书必须明确只读：不编辑、不暂存、不提交、不改配置。实现者负责修改，reviewer 负责问题、证据和裁决；`scout` 可调查事实，但不能替代正式 reviewer 的审计结论。需要专业领域知识时，读取适用 skill 后明确审计判据。

怀疑 reviewer 越界时，先核对工具足迹和文件归属。不能把怀疑写成已发生的事实，不能自动回滚可能属于用户的改动；确有越界修改时分离修改与审计，由独立 reviewer 重审。

### 原始需求透传与 reviewer 提问

当用户要求 reviewer 与主代理对抗，或用户指出主代理的概述可能失真时，审计请求必须包含用户原始需求，而不是只给主代理的转述：

- 逐字引用审计所需的最小相关原话；较长材料仅在用户授权的项目本地位置提供精确引用，不复制到共享 skill。先检查私密内容，无可用材料时请求必要原句，不编造需求。
- 标明本增量覆盖哪几条原始需求，哪些明确不在本增量范围，以及未覆盖项依赖哪个后续增量。
- 给出精确的 commit hash，或能定位固定差异的 diff 标识；reviewer 能核对实际改动，而不只收到可变的 diff 命令。

reviewer 可以就用户原始需求向主代理提问。问答遵守：

1. reviewer 引用原始需求的具体句子，指出实现或证据与这句话的差异。
2. 主代理用文件、行号、命令输出或提交哈希回答，不用“我理解为”“设计上应该”替代证据。
3. 回答需要改变需求解释时，先让用户确认，不自行改写需求。
4. 未回答的问题、未解决的差异计入阻断项；不得用“已向 reviewer 说明”当作通过。
5. 问答摘要和原始引用写入 `progress.md` 的插入询问或审计结论。

对抗性审计的结论只回答“实现是否满足用户原话”，不以主代理的自审、测试通过或计划完整代替。

如果 reviewer 发现阻断问题，先修复、重跑、重新审计。存在已知阻断项时，不进入下一个依赖增量。

独立增量可以在某个审计等待时继续，但所有增量都有结论之前，不能把分支说成完成。

### worktree 规则

已获提交授权时，不留下已完成但未提交的增量后继续依赖项。未获授权时，以明确的工作区 diff 和审计结论完成检查点，不擅自提交，也不把未提交误报为未完成验证。

worktree 里只应保留：

- 当前正在实现的增量；
- 有记录、有意阻塞的条目；
- 已验证、已审计但没有提交授权的改动；
- 你没有触碰的用户改动。

## 证据新鲜度

reviewer 的 approve 只对具体的 commit 或 diff 标识所对应的那份差异有效。

- 修复、rebase、merge、cherry-pick 或改写提交后，重新验证受影响部分；
- 审计判据、领域规则或用户需求改变时，重新审计受影响范围，即使代码没变；
- 在目标分支或当前工作区上记录新的代码标识、环境、运行对象和审计范围；
- 旧 main 上的测试不能证明合并后的 main；
- 不能重跑时，状态记为 blocked，不写成通过。

## 停止条件

- reviewer 提出阻断：修复、重跑、重审；修不动就停，不进入依赖项。
- 环境/权限阻塞：记录已验证差异、阻塞和下一步；只有已获授权才提交，不扩大权限，继续不受阻的独立工作。
- 上下文丢失：先按增量记录表恢复；恢复不了就停下来问，不猜。
- 用户要求停止：保留增量记录表、已提交增量和已审计未提交的工作区改动，不清理用户数据，不继续扩展范围。

## 提交检查

每次提交前：

先核对用户是否明确要求提交，以及授权涵盖哪些文件和操作。没有提交要求时，本节不触发；“继续”“修好”或 reviewer 的 approve 都不是提交授权。

1. 只暂存本增量涉及的文件。
2. 检查 `git diff --cached --name-status`。
3. 运行覆盖本增量的验证命令。
4. 使用中文 conventional commit；写明实际命令和结果。
5. 检测本地是否有可用 GPG 签名私钥；存在时通过 ask 让用户选择签名或不签名，多密钥且选择签名时再确认密钥。没有可用密钥且用户要求签名时停止；签名失败不自动降级，不写入个人密钥或修改全局配置。

没有明确授权，不使用 `--amend`、squash、rebase 或其他改写历史的操作。合并和推送分别核对授权；获准合并时使用 `--no-ff`。目标 worktree 有用户改动时保持原状，选择隔离工作区或取得处理授权，不自动 stash、清理或覆盖。

## 证据等级

| 等级 | 证据 | 可以宣称 |
|---|---|---|
| 契约 | 单元/集成测试、错误分支 | 该行为符合契约 |
| 反例 | 旧状态、ABA、race、清理、并发路径 | 该失败模式已有测试覆盖 |
| 真实目标 | 实际进程/设备/网络路径 | 该目标在该场景可用 |
| 重复运行 | 同一命令/profile 多轮 | 在声明范围内结果稳定 |
| soak | 长时间资源/身份观察 | 测试时长内增长有界 |

使用能真正证明结论的最低等级。高等级的数字不能抵消低等级的失败。

## 现场保护与运行对象

- 故障调查先用现有日志、指标、连接状态和已开放的 profile 只读取证。重启、替换二进制、修改诊断配置、暂停或终止进程会改变现场；先说明丢失的证据、影响与恢复办法，并核对明确授权。
- 先识别已有服务与测试的 PID、端口、二进制版本、负载及所有者；能从工具查到的事实直接查，不要求用户重复提供。用户已启动的实例优先复用，不另起一份冒充同一现场。
- 只清理本次任务启动、已记录身份且获准清理的进程；进程名相同不是所有权证据。无法安全取得证据时保留未验证结论，不编造根因。

## 并发、身份与资源所有权

修改共享状态、锁或异步回调前，先写清：

- 每种 ID 表示什么实体、在哪个范围唯一、何时失效；相同格式不代表同一身份，不把连接、设备、进程等标识直接合并；
- 谁拥有状态、谁能修改或删除，旧连接的延迟回调能否误删新连接，失败、取消、关闭和重试后如何收回资源；
- 每把受影响锁保护什么不变量、锁序与持有范围，是否跨 I/O、回调或网络发送，队列和后台任务如何结束。

用旧代删除新代、重复登记、取消与关闭竞态等反例验证。并发与性能变更交给适用领域 reviewer，不能用单元测试或 race 检查通过代替锁序、死锁、饥饿和资源有界性审计。

优先选择能简化不变量的单所有者或不可变快照；不要为追求“无锁”引入更难证明的原子协议。必须加锁时说明理由，并审计同一路径的既有锁，不只审新锁。

## 性能附录

当任务是性能优化时：

- 先固定同命令、同 profile、同指标定义的可比基线，记录被测程序版本、资源、采样节奏和阶段；存在独立负载端时也记录其版本与配置，涉及断连时记录断连/重连参数。计时分段或压测器行为变了就重建基线，不能把数字下降直接当作加速。
- 进程内 benchmark 只证明该路径和负载；幂等重报不是新连接吞吐，稳态成功也不证明高频断连恢复成功。
- 运行前从当前任务约定适用的必测指标、重复轮数、验收阈值和波动上限，例如吞吐、尾延迟、错误和资源增长；连接型负载还应约定在线数、断连恢复等指标，不适用项不列为必测。不得套用旧项目的固定人数、比例或秒数。需要稳定性结论时使用至少三轮同配置运行。
- 只用已结束、同阶段的完整轮作结论，中途样本仅表示进度。逐轮报告事先约定的全部主指标、失败轮和未测项；`errors=0` 不能抵消其他主指标失败。主指标失败就是该轮失败，缺少约定的必测指标就是 blocked，不能只挑最好一轮。
- 区分负载端端口、CPU、内存耗尽与被测程序的失败，记录归因证据；涉及断连负载时单独观察断连停止后的恢复。用户现场报错不能被聚合指标或另一轮成功覆盖。
- 任务涉及端到端延迟时，说明计时分段、吞吐、恢复与资源代价；ACK 只是连接型场景的一个例子。重复轮超出波动上限或持续恶化时，不宣称稳定。
- 热路径日志可能干扰被测对象。削减日志前保留必要的有界计数、分段计时或采样，说明损失的定位能力和观测开销；避免无界事件缓存和按实体增长的高基数标签，覆盖日志启用与过滤两类路径。观测本身也要用同一负载验证。

引用约束前核对当前权威规格、代码与测试；历史快照、旧决策和注释只作背景，不能冒充现行兼容契约。正确性、身份、生命周期和必要兼容约束优先于性能。如果规格疑似阻碍优化，先调查约束的目的和兼容依赖，给出替代行为、迁移代价及 reviewer 证据，请用户批准后再改规格与实现；不悄悄绕过条款，也不把规格当作不能质疑的结论。

用户指定先交付稳定方案、再探索替代方案时，按顺序完成稳定方案的验证和审计；只有获得相应授权才合并，再用独立工作区研究。研究分支的单轮改善不能覆盖稳定基线，也不能自动获得合并授权。

## 状态契约

只用这三种状态：

- **未实现**：没有实现，或实现没有生产调用点。
- **已接入未验证**：已接线，但没有真实目标上的成功证据。
- **实机验证通过**：命令、时间、对象标识、原始输出和重复证据等级都与声明一致。

合并不是验证等级。若在重复验证通过前已合并，保持 **已接入未验证**，记录失败轮次，保留分支或开关；回滚必须得到明确批准。

## 规则缺口与经验提炼

当现有规则不能表达当前情形、相互冲突或出现新反例时：

1. 区分已观察事实、假设和缺少的证据；保留未验证状态，不从一次结果发明普遍法则。
2. 如需调查，给只读 `scout` 精确问题和当前仓库中已授权的最小证据；材料不存在时查现有代码与可观测行为，不依赖预置会话备份，也不擅自复制私密记录。
3. 要求返回规则候选的四项：触发条件、动作、验证证据、反例，并标明事实引用与不确定性。
4. 主代理复核引用与适用边界，用可执行场景检查规则；领域正确性由适用 reviewer 裁决，scout 的分析不能代替审计或运行验证。
5. 只把去标识的通用规则写回 skill；项目阈值、主机、账号、路径、提交清单和原始日志不随规则分发。

模型在没有新增规则时已作出正确决策，就如实记录，不虚构失败基线或宣称规则带来了未测出的改善。

## 与 nLsyntax 的交叉触发

写审计报告、提交说明、skill/规则文档或给用户的完成说明之前，按 `nLsyntax` 检查：

- 是否用了需要读者二次解码的比喻；
- 是否能用对象、动作、数量、失败条件替代；
- 是否把一个比喻换成另一个；
- 是否只对实际读者需要的术语补充解释，并保留标准技术名称及用户原词。

`nLsyntax` 在多步骤交付的审计、提交和汇报中反向引用本 skill；本 skill 在写这些文字时引用 `nLsyntax`。

## 汇报

每次交付汇报写明：

- 状态；
- 增量和对应提交或已审计的工作区差异，以及提交授权状态；
- 跑过的命令及结果；
- 仍有哪些未提交、被阻塞或超出范围；
- reviewer 结论；
- 已知失败及归属证据；用户报告的失败直接登记，没有独立证据时不擅自标成“无关失败”。

不要因为测试通过、reviewer 同意或分支已合并就写“完成”。写清验证了什么，没验证什么。

## 应立即停止并检查的信号

- 已获分阶段提交授权，却说“所有部分做完再一起提交”。
- “reviewer 最后看整个 worktree 就行。”
- “第一部分只过了测试，我可以不审计就开始依赖的第二部分。”
- “流程要求及时提交，所以没授权也要提交。”
- “reviewer 可以边改边审，自己 approve 就行。”
- “已经合并了，所以已经验证。”
- “只跑相关测试就够了，全仓失败不用管。”
- “把所有 server 进程都杀掉。”只能清理本次任务启动、身份仍匹配且获准清理的进程；知道 PID 或端口不等于拥有该进程。

## 隐私与可分发边界

skill 只携带通用规则、可复用工具和不含项目数据的模板。不得保存原始或压缩会话、事故日志、凭据、账号、主机与设备标识，或包含这些内容的摘要、截图、校验清单。

`.gitignore` 不是隐私隔离：未跟踪的文件仍可能被本地读取或打包。分发前检查隐藏文件、忽略文件、压缩附件与缓存中的旧路径；只验证普通文本搜索不足以证明无残留。

用户要求删除私密数据时，先提炼获准保留的通用规则，再删除指定原件、压缩副本、摘要和失效引用；不另建备份，不移动到另一个 skill 继续保存。删除工作区文件不等于清除版本历史或外部副本；未获授权不改写历史，并明确尚未处理的范围。
