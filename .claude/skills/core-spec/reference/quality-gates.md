# Core Spec 十门质量检查表

本文件是 core-spec skill 的最低验收。新建或发生行为变更的 spec 缺设计图不能宣称完成；未触及行为的存量 spec 登记迁移债务，不仅凭新门追溯改写既有状态。审计先看 `### 1.0 设计图景` 能否从入口走到结果，再按本表打分。

---

## G0 设计图

**目标：** 读者不看决策编号，也能从入口走到结果。

- [ ] `### 1.0 设计图景` 存在，是纯 ASCII 树。
- [ ] 每个动作节点写明谁、对象、动作；实际可达的成功/失败分支有观察与后继；终点写结果及终止条件，不虚构分支。
- [ ] 同一种失败只有一个后继。
- [ ] REQ、状态机、决策日志没有图上不存在的后继。
- [ ] 存量 spec 缺图时登记为待迁移；下一次行为变更先补图。若已发生行为变更却尚未补图，明确标为 G0 未满足，不能用旧审计器 PASS 宣称完成。
- [ ] 新模板审计器只检查标题和非空正文；图上路径能否成立、图与投影是否一致，必须人工核对。

## G1 精确与可追溯

**目标：** 规范性条款没有第二种读法，每条需求都能定位到唯一 ID 和验收标准。

- [ ] 全文无模糊词：可能、大概、尽量、友好、快速、及时、合理、适当、支持等词不得出现在规范性条款；确需表达概率/范围时给出数值（P95、±10%、≤5s）。
- [ ] 每条功能需求有唯一 ID（`REQ-<n>`），且 ID 不重复、不复用已删 ID。
- [ ] 每条需求包含：角色 + 动作 + 价值（用户故事），以及 `Given/When/Then` 验收标准。
- [ ] 每条需求标注优先级（P0/P1/P2）。
- [ ] 时间、容量、次数、状态数全部是具体数值；禁止“若干、多个、一批”。
- [ ] API/数据结构示例完整：请求、响应、错误路径至少各一例。
- [ ] 正文无实施波次标识；实施推进安排写入 `plans/` 或 roadmap，不得混入权威规格正文。

## G2 异常与 NFR 完整

**目标：** 不只写 Happy Path；上线后最常见的故障模式在 spec 里有规定。

- [ ] 每个状态写明进入条件、可观察结果，以及实际可达的退出条件和失败分支；终点状态明确终止，不编造退出。
- [ ] 状态图中每条可达转换写明触发条件、必要的 guard、可观察效果；存在失败分支时写明失败去向。
- [ ] 错误模型覆盖：未入队/入队后断线/超时/取消/重复回包/过期代际/资源耗尽，并区分“事实”与“建议”。
- [ ] NFR 单独成节且量化：
  - 性能：延迟（含 P95）、吞吐、并发；
  - 可用性：恢复窗口、重试次数、退避上限、降级行为；
  - 安全：认证、授权、敏感数据、日志脱敏、限流；
  - 合规/保留：数据保留周期、清理策略；
  - 容量/背压：队列上限、溢出行为、无界扩容禁止项。
- [ ] 明确“不做自动重放/自动恢复”的边界，把重试决策留给知道幂等语义的一层。

## G3 内部一致

**目标：** 图、表、正文、验收标准、目标/非目标是同一套语义；一个术语只有一个定义。

- [ ] 术语表覆盖所有规范性名词；同一概念全文只用同一个词（含代码标识符）。
- [ ] 同一数值承担不同语义时必须分别命名并定义；不得仅因单位相同就合并计时或计量规则。
- [ ] 同一类型/方法/错误在全文只有一处权威定义，其余地方只引用，不复述签名。
- [ ] 状态图、状态表、正文规则、验收标准相互一致；任何一处修改必须同步其余各处。
- [ ] 被取代条款已原地合并或删除；权威规格正文不得出现“（已被 Dxx 取代）”“补丁标记”字样。
- [ ] 正文无实施步骤与实现级设计：迁移步骤、锁算法、波次推进等要么移入 plans/，要么压缩为可验证的一句话契约。
- [ ] 目标/非目标与最终验收一致；若验收推翻早期目标，早期目标必须改写，不能并存。

自检方法：把 spec 中每个状态、错误、方法名列成清单，逐一对照代码与验收；发现两个来源说法不同即 P0。

## G4 验证实测全绿

**目标：** spec 的每一条关键契约都有机器证据，且这些证据在提交时真实跑过。

- [ ] `tools/audit_spec.py` 存在且 PASS（结构审计）。
- [ ] `tools/test_audit_spec.py` 存在且 PASS（审计器负例自测：每类违规都要有 fixture 能让审计器失败）。
- [ ] `tools/barriers.py` 存在；spec 为 authoritative 时必须实际运行且全绿，禁止只写命令不运行。
- [ ] manifest 中声明的每个测试锚点都能在代码中 grep 到真实测试函数名；缺失即失败。
- [ ] manifest 中声明的代码契约 pattern 与代码一致；旧签名/旧 sentinel 已列入 obsolete 且零命中。
- [ ] 新增/修改 spec 后，spec 与代码同批提交，审计命令输出写入提交说明或验证记录。
- [ ] 存量 spec 迁移时保留已通过验证的既有工具，只改 canonical 文件名与路径，不得替换成模板实现；旧全局脚本在新位置全绿后才删除。

## G5 治理与元信息

**目标：** 任何一条规范都能回答“为什么这么定、哪次变更定的、现在是否还成立”。

- [ ] 每条规范性契约都能归因到决策日志中的决策 ID（D01、D02…）。
- [ ] 决策 ID 范围全文档一致；不得出现“覆盖 D01–D24”而实际已有 D25 的过期引用。
- [ ] 头部元信息完整：状态（draft/authoritative）、版本、受众、范围、治理规则、变更历史指针。
- [ ] 变更日志/历史指针存在：git 可追溯之外，history/ 或决策日志能定位每次行为变更。
- [ ] Out of Scope 明确列出本次不做的事，防止范围蔓延。
- [ ] 提交遵循仓库 AGENTS.md 约定（提交信息、签名方式、spec 与代码同批）。

## G6 外部输入域闭合

**目标：** 设计图上会到达的外部输入有定义行为。不把不会走到的组合写成表格来充数。

- [ ] 设计图上的每个可达外部输入写出实际存在的成功/失败观察和后继；无需虚构无失败分支。
- [ ] 只为图上会到达的输入写业务后继。不要求全部取值域的笛卡尔积；若采用全格矩阵，不可达格标为「不可达」而非业务后继。
- [ ] 每格标注该组合下的端到端可观察结果；由其他模块裁决的后果必须注明消费方与裁决层。
- [ ] 矩阵与状态图、转换表、异常表互相一致：修改任一处必须同步其余各处。
- [ ] 风险覆盖按目标系统的风险分析选择高风险输入，并关联相应验证锚点；不要求声称发生过事故。
- [ ] draft→authoritative 前，覆盖所有可达且行为不同的输入格子的表驱动测试存在并纳入 barriers；不可达格子不要求测试。

常见反模式：漏掉可达但不常见的失败输入；矩阵格写了行为但状态机转换表里找不到对应转换；把本应属于下游模块的判断职责（例如可用性探测）混进本层矩阵格。

## G7 内嵌可执行语义（内部一致性）

**目标：** 状态机等可机械验证的契约可嵌入 spec.md，由工具提取、编译执行，避免维护独立语义副本。

本表中针对 `SEMANTICS` 标记、`Semantics` 模块和 `LABEL` 围栏的约束仅适用于旧代格式。新代 `ORACLE` 为 opt-in，使用独立接口与标签围栏；不要求旧代 `edges`/`transition` 导出。详见 `oracle-contract.md`。

**单一规格源：** spec.md 本身就是唯一规格源，嵌入的 Haskell 是 spec 的可执行部分。禁止 `spec.md → 人/AI理解 → 独立.hs文件` 的多层翻译——每多一层多一次语义漂移。AI 可以帮助编写 spec（含嵌入代码块），但不能成为 spec 到语义之间的解释器；把 AI 完全拿掉后，系统必须仍然独立、稳定、可复现工作。

- [ ] spec 含状态机时，spec.md 有带标记的嵌入代码块（```haskell，模块名 `Semantics`，由提取工具按标记定位）。一个 spec 可以有多台，每台一个 `SEMANTICS:<name>`。嵌入语义是预言机：判定观察是否合法，不规定实现调用顺序。
- [ ] 代码块为纯声明：无 main、无 stdio、无文件 IO、无序列化代码；**零字符串字面量**（渲染/解析文本全部归固定驱动）。
- [ ] 嵌入代码注释只描述代码语义（类型含义、决策 ID、事件触发条件）；不包含对读者说的话、不重复 spec 散文叙述。
- [ ] 嵌入块之后有 ` ```LABEL:<name> ` 围栏（state/event/note 中文标签，工具侧数据）。
- [ ] 标签围栏之后有 RENDERED 锚点包裹的 ```mermaid 状态图，内容与驱动 render 输出一致（barriers 实跑 diff），禁止手改；图是状态图（非表格罗列），no-op 边已折叠。
- [ ] 状态机图不手绘；命名与说明只出现在 LABELS 块一处（散文不重复命名映射）。
- [ ] 提取/编译/执行由共享屏障 + 固定驱动（`.claude/skills/core-spec/tools/driver/SpecDriver.hs`）承担。
- [ ] 已有嵌入块若编译器要求全格，则显式列出，无 catch-all。全格是编译要求，不是设计。不可达格只作非业务占位并注释为不可达，必须检查驱动不会把它当成合法业务后继；禁止为补满全格新增事件。`ghc -Wall` 零 `incomplete-patterns` 只说明格子写了，不说明设计对。
- [ ] 不变式仅限 spec 条款中确实存在、需要跨状态验证的全局/时态性质（可达性、无循环、单调性）；复述迁移表的规则不写——单一来源原则。
- [ ] 屏障求值嵌入语义：全部性质 PASS，失败必带最小反例。
- [ ] 提交的快照是 `snapshots/<name>.oracle.snap.gz`（确定性无损 gzip：`MTIME=0`、无 `FNAME`/注释、level 9——同一全文同一字节）；**解压后的完整全文**与嵌入代码块重新求值输出按 `norm_eol` 语义一致（全文比较：不存 hash、不抽样、不做前缀/长度近似；barriers 实跑，禁止只写命令不运行）。
- [ ] 快照存储异常一律硬失败（退 1，不得退 3 冒充未验证、不得截断或缩水当通过）：坏 gzip / 截断 / CRC 不符 / 尾随非 gzip 数据 / 非 UTF-8 / 解压超 512 MiB / 落盘超 64 MiB；旧明文 `.oracle.snap` 不作验收来源（单独存在或与 gz 并存都失败），迁移只发生在 `--oracle --update-snapshot`：先对全部机器编译求值合法，再整组落盘；既有 gz 解压后等价则不重写（字节与 mtime 稳定），旧明文在 gz 原子替换成功后才删除。

## G8 语义一致性检查（spec↔实现）

**目标：** 收尾时由独立 reviewer 对照现行规格、实际实现与测试证据，判断实现的可观察行为是否符合规格。评审是语义判断，不包装成机械证明，也不改变规格提取、编译与测试的确定性执行要求。

**与 G9 的区别：** G8 检查规格与代码是否一致；G9 检查设计图、嵌入语义及标签本身是否正确。两项可以同次评审，但必须分别给出结论。

- [ ] 收尾 reviewer 阅读现行 spec 的设计图、REQ/AC、嵌入语义（如有）及实际实现，逐条核对可达的成功、失败、取消路径与边界行为，不能只看模型或审计器输出。
- [ ] 评审报告给出规格条款、代码文件/符号/行号、实际测试命令与结果，明确区分代码阅读判断与已执行测试；不能仅写“无问题”或“与规格一致”。
- [ ] 未实现、未验证或与规格不一致的必需行为明确列为未闭环 `BLOCKING:`；规格领先代码不能按已实现通过，缺少证据不能按已验证通过。
- [ ] 评审记录标识所审规格版本及实现提交或差异范围；相关规格或实现变更后，重新核对受影响条款，旧结论不能直接复用。
- [ ] G8 不要求新增专用运行记录、rawfacts/trace 协议、`traces/` 语料提交或重放系统。已有真实运行证据可以辅助评审，但不替代 reviewer 的语义检查，也不能伪造或改写历史证据。
- [ ] G4 的实际测试和 G9 的规格内部评审仍须满足；G8 通过不能替代它们，也不能仅凭测试 PASS 推定 G8 通过。

## G9 评审门（AI 可辅助）

**目标：** 设计图、语义与标签的正确性无法机械判定，交给人工或 AI 辅助评审；AI 也可协助编写正文，但不能成为规格提取、编译、执行的解释器。门本身只检查留档与哈希，保持确定性。

- [ ] 标签完整性：每个 state/event 有标签，标签与说明不引用不存在的名字（驱动 render 时校验，缺失即报错）。
- [ ] 有设计图时，评审材料含图、语义与标签，留档哈希与三者一致；改图后旧留档失效。存量缺图仅保持旧哈希兼容，不能据此宣称 G0 通过。
- [ ] 留档中无未闭环 `BLOCKING:` 项。
- [ ] 留档按事件核对标签和每一条会走到的迁移。标签声明的效果与迁移不符，或两个事件标签相同效果不同，必须是 `BLOCKING:`。只写「无阻断项」不算评审。
- [ ] 评审流程留痕：`--emit`（材料）→ 评审 → `--record`（留档，含模型名与日期）。

## 常见借口与回应

| 借口 | 回应 |
|---|---|
| “这段行为代码里已经很清楚，spec 不用写” | spec 是唯一权威，代码只是当前实现；不写就无法发现漂移。 |
| “审计器 PASS 了，所以没问题” | 词法检查不看设计图。图上的失败没有唯一后继，门绿也是没写完。 |
| “全格写满了，所以后继齐了” | 全格是编译要求。图上没有的格子不是设计。 |
| “先把旧条款留着，标注已取代，以后再清理” | 一份文档两套语义；保留旧条款的收益永远低于误读成本。 |
| “这个测试名计划里会补，先写进 spec” | 允许 draft 状态声明 planned，但 authoritative 前必须真实存在且 barriers 全绿。 |
| “验证命令跑过了，只是没记录” | 没有可复现输出等于没有验证；把命令与结果写进提交说明。 |
| “spec 已经写了就必须照做，不能停” | spec-first 不是条款不许质疑。身份分层错误、What/How 混写、决策假设被推翻时，立即告知用户商量是否改 spec；确认前不得一条路走到黑。 |

## 审计输出格式

审计报告至少包含：

1. 验证命令与真实输出（audit_spec / test_audit_spec / barriers）。
2. P0/P1/P2 分级问题清单，每条带 spec 行号与代码/测试证据。
3. 整改顺序：先语义、再契约、再可验证性、再元信息。
4. 明确结论：`draft` / `authoritative` / `需回退重审`。
