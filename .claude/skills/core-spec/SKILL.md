# Core Spec（核心权威规格）

## Overview

Core spec 的正文是一张设计图，加上这张图迫使写下来的少数规则。规则是最低要求。门通过不是设计完成。

设计图回答：一次工作从入口到结果，谁对哪个对象做什么；成功看见什么；失败看见什么；下一步是图上的哪一步。读图的人不用先懂决策编号和事件名。

规则只写两个实现者会在同一步做出不同后继的地方。每条规则必须指回图上的一步。指不回的规则删掉，不留在正文里等审计。

验证脚本、决策编号、短语出现次数、状态×事件全格，都是图的投影。投影缺了后继，先改图，再改投影。投影缺了一个短语，缩小审计规则，不发明句子去填。

**术语约定：** 权威规格、单一事实源、规格契约、验收屏障。不使用「活文档」。

**什么算写完：** 图上每条会走到的路径都有可观察结果；有成功/失败分支的动作写清两者的观察和后继。终点明确终止，不编造下一步或失败分支。不是审计器 PASS，也不是性质门全绿。

## 设计图（先写这个）

放在 `spec.md` 的 `### 1.0 设计图景`。用纯 ASCII 字符绘制树（如 `|--`、`+--`）。每个动作节点写清谁、对哪个对象做什么；实际存在的成功/失败分支写明各自观察与下一步。终点只写结果及终止条件，不为凑字段虚构分支。阶段号、级别、层号不能单独当节点。规格里的简称只能放在括号里，括号前的句子必须已经说完动作。

图只画会走到的路径。不画为了填满表格而存在的空转移。同一对象、同一前置条件下的一种失败只有一个后继。新模板审计器只机械检查标题和非空正文；图是否可实施、路径是否完整必须人工审查。存量规格缺图或本地审计器尚未升级时，记录为待迁移，不能把旧工具 PASS 当成 G0 通过。

嵌入状态机、REQ、决策日志是这张图的投影：

- 图上有的失败，投影里必须有同一种后继。
- 投影里多出来的事件，若图上没有对应节点，删事件，不补图去迁就事件。
- 两个事件标签相同、效果不同：留下图上那一个，删另一个。
- 标签声明事件具有某种效果，但某条会走到的迁移未体现该效果：这是阻断，不是说明文字可以补上的。

评审留档必须按事件核对：每个事件的标签，对照该事件每一条会走到的迁移。对不上就写 `BLOCKING:`。性质门 PASS 不能代替这一对照。

## 本质

spec 写应该是什么，不写现在代码是什么。领先代码只在领先的是这张图时成立。图能照着做、代码还没做，是正常的领先。图是一组不能拼成一条路径的句子，不是代码落后，是图错了。先告诉用户，不继续补规则。

**「默认代码未跟上 spec」的适用范围：** 仅当目标行为条款本身未被推翻、只是代码尚未实现该目标。不适用于条款自相矛盾、身份分层错误、把目录/搬家/import 前缀等 How 写进行为 spec。那一类是 spec 假设被推翻，不是代码落后。

**自省（发现问题必须停手）：** spec-first 不是「条款永远正确、执行者不许质疑」。权威约束的是已确认的目标行为；它不授权把写错的条款执行到底。执行本技能任一流程（新建、变更、审计、迁移、对照代码实施）时，一旦发现必须停手的信号，**立即用中文告知用户，给出证据与可选调整，等待确认**。用户表态前：不得继续按该条款改代码，不得为了让 audit 变绿而把错误布局或错误身份写进更多文件，不得一条路走到黑。

spec 有两条腿，缺一不可：

- **领先腿（目标行为）**：接口签名、状态机、错误模型、进度/重试/取消语义——定义"应该是什么"，可以领先代码。
- **根植腿（代码事实引用）**：错误码映射表、常量数值、符号名、既有签名——引用"代码里真实存在的事实"，必须与代码一致，不得凭空定义。

## When to Use

符合任意一条即启用本技能：

- 要定义跨模块、跨进程、跨端的契约：接口签名、状态机、协议语义、错误模型；
- 规格将作为长期唯一权威，plan 和代码都以它为准；
- 写 implementation plan 之前发现没有权威 spec，或现有 spec 无法支撑实施；
- 审计、变更现有核心 spec；发现 spec 与代码漂移、验收屏障失败、决策无法归因。

不启用本技能（走普通设计文档/注释）：

- 一次性 bug 修复、单模块内部实现说明；
- 内容不产生跨实现方契约、不需要长期权威。

## 与 brainstorming

对齐默认走 superpowers:**brainstorming**（一问一答、方案 2–3、分段设计、yes 才继续）。本技能是规格落点，不是访谈。

- brainstorming 若要把设计写成文件：写 **本技能的** `docs/specs/<name>/spec.md`，不要写 `docs/superpowers/specs/YYYY-MM-DD-…-design.md`。用户对 spec 位置的偏好见仓库 AGENTS.md，覆盖 brainstorming 默认路径。
- 触及已有域契约 → 走下面「变更权威规格」，不要另开一份日期戳设计文档。
- `.claude/skills/knowledge` 负责写 `CONTEXT/` 目录与 ADR；多轮访谈仍走 brainstorming；落规格仍走本技能。
- 下游只接 superpowers:**writing-plans**。

## 目录契约

每个 core spec 必须长这样：

```text
docs/specs/<spec-name>/
├── spec.md                    # 唯一权威规格正文（含嵌入可执行语义代码块）
├── tools/                     # 本 spec 自带的验证工具，从 templates/tools 复制
│   ├── audit_manifest.json    # 唯一事实源：术语、决策、契约、锚点、屏障
│   ├── audit_spec.py          # 结构审计器（部分机械检查；不能替代十门人工核对）
│   ├── test_audit_spec.py     # 审计器负例自测（每类违规都要能失败）
│   ├── barriers.py            # 验收屏障运行器（有代码后必须全绿）
│   └── README.md              # 本 spec 验证命令与状态说明
├── issues/                    # 问题/风险登记（调查记录，非规范性正文）；一个问题一个文件，命名 YYYY-MM-DD-<中文短slug>.md
│   └── README.md              # 本目录规则、文件骨架与状态总览，从 templates/issues 复制
└── history/                   # 日期戳冻结快照，只读不更新
    └── README.md
```

硬性规则：

1. 验证脚本**只允许**放在 `docs/specs/<spec-name>/tools/`，与 spec 同目录、随 spec 提交；不得散落在全局 `tools/`。
2. 每个 spec 的 tools 是**自包含副本**，从本技能模板复制后独立演化；修改通用规则要先改本技能的模板，再逐 spec 迁移。`audit_manifest.json` 的 `audit_baseline` 只表示本地结构审计器与负例已验证的规则基线，不是正文业务版本，也不证明 G0 语义正确；旧清单未标注时不得仅凭哈希认定落后。
3. `spec.md` 是唯一权威；`history/` 只放冻结快照，任何人在快照上做“补丁式修订”都算治理违规。
4. `issues/` 只放问题/风险调查记录，不放规范性条款；一个问题一个文件，命名 `YYYY-MM-DD-<中文短slug>.md`，骨架见 `templates/issues/README.md`。
5. issue 状态原地流转：`open` → `resolved`/`wontfix`；`resolved`/`wontfix` 必须填写 §9 决策 ID；不迁入 `history/`。
6. spec 的提取/编译/验证工具**共享于 skill**（`.claude/skills/core-spec/tools/`），禁止复制到 spec 目录或散落到项目级 `tools/` 等目录；spec 的 `tools/` 自包含副本约定不变（仅 audit/barriers 三件套）。
7. spec.md 内嵌的 Haskell 代码块是 spec 正文的一部分，随 spec 同批提交；禁止在 spec 外维护独立 .hs 文件作为语义源。

## 自省：必须停手告知用户的信号

非穷举。命中任一条即停，先商量，再决定改 spec 还是改代码。

- 条款把不同身份的对象放在同一层，或行为 spec 写入纯 How（目录分组、import 前缀、搬家名单），而相关行为条款已否定该结构。
- 新证据推翻 §9 某条决策的假设；继续执行会扩大错误面（例如把错误路径锁进 manifest，或按错误决策 ID 批量替换）。

告知时必须有：发现了什么、证据在哪（spec 行号 / 决策 ID / 与另一条款的矛盾）、建议怎么调（改 spec / 缩小条款 / 不改）。禁止自行选定后继续实施。

用户确认改 spec 后：先归因新决策 ID，或把被推翻的条款原地合并/删除，再改正文与 manifest。这仍是 spec-first，只是先承认假设错了。

## Spec 正文边界

spec 正文必须先写 `### 1.0 设计图景`，再写背景/目标/非目标、术语表、系统模型与状态机、功能需求与接口契约、错误模型、NFR、异常与边界、验收标准、决策日志、验证入口。没有设计图，后面各节不算写完。
spec 正文不得写实施波次、迁移推进、具体迁移步骤、锁算法与实现级设计细节、问题调查过程与未闭环风险。这些内容写入 `plans/`、独立设计文档或 `issues/`；spec 只保留决策 ID 归因、可验证契约摘要与指针。

调查中尚未通过 §9 决策日志闭环的问题与风险记录在 `issues/`；正文只保留由决策 ID 归因的结论。

例外：当某实现约束本身构成跨层公开契约（如锁序、发送语义）时，只保留可验证的一句话契约，不写推导过程与历史推进。

## 内嵌可执行语义（spec 内代码块）

spec 中含状态机或可机械验证契约时，**不建独立模型文件**——Haskell 代码块直接嵌在 spec.md 的对应章节里，由固定工具机械提取、编译、执行。原则：

- **单一规格源**：spec.md 本身就是唯一规格源，嵌入的 Haskell 是 spec 的可执行部分，不是独立解释。禁止 `spec.md → 人/AI理解 → 独立.hs文件` 的多层翻译——每多一层多一次语义漂移。
- **AI 不进入 correctness path**：AI 可以帮助编写 spec（含嵌入代码块），但不能成为 spec 到语义之间的解释器。把 AI 完全拿掉后，这套系统必须仍然独立、稳定、可复现工作。
- **提取工具是固定的**：共享屏障从 spec.md 按标记提取代码块，调用**固定驱动**（`.claude/skills/core-spec/tools/driver/SpecDriver.hs`，含 IO/字符串，属工具侧）编译执行。模型侧保持纯声明，渲染/解析/报告全在驱动侧；提取规则不因 AI 判断而变化。
- **预言机，不是语言机**：嵌入语义判定「观察到的事件之后，什么后继与观察是合法的」。效果列表是该步必须成立的观察，不是必须调用的函数。禁止把实现步骤（函数名、调用顺序）写成迁移效果。规格与实现的一致性由 G8 收尾 reviewer 对照代码和测试证据检查，不要求实现侧新增专用迹线记录或重放系统。
- **旧代 `SEMANTICS` 模块约定**：以下导出面只适用于旧代 `SEMANTICS`。每个旧代嵌入块编译时声明 `module Semantics`（该次编译的固定 import）。一个 spec 可有多台旧代预言机（多个 `SEMANTICS:<name>` 块），每台单独编译、单独快照、单独评审。驱动不写死状态名或性质名。旧代模块必须导出 `states`、`terminalStates`、`events`、`initialState`、`edges`、`MS`（位置构造 `MS state Bool`）、`msState`、`stepWith`、`transition`、`Edge`、`propertyResults :: [(propName, Int)]`（`propName` 用 `Show`，模型内禁止字符串）、`traceExempt`（无豁免则恒 `False`）、`data Detail` 与 `marks :: MS -> [Detail]`（构型细节，空列表表示无标记；出现过的构造子必须在 LABEL 里写 `detail 构造子 = 中文`）。新代 `ORACLE` 是 opt-in，接口不使用这组 `edges`/`transition` 导出；见 `reference/oracle-contract.md`。
- **跨 spec 引用**：嵌入块里可写一行 `corespec import <spec目录名> <SEMANTICS名> as <别名>`。这行不是合法 Haskell，禁止写成注释。`spec_barrier.py` 在调用 ghc 之前把它改成 `import qualified <别名>`，并把被引用块的 `module Semantics` 改成该别名后一并编译。别名必须是大写开头的 Haskell 模块名。成环、找不到 spec、找不到 SEMANTICS 块，编译门直接失败。被引用模型仍以自己的 spec.md 为唯一源，不复制到引用方。
- **标签围栏**：嵌入块之后附 ` ```LABEL:<name> ` 围栏，逐行 `state X = 中文名`、`event X = 中文名`、`note X = 说明`——工具侧领域标签（模型零字符串，标签只能放这里），供驱动渲染；带类型围栏使其在渲染视图里显示为规范代码块。
- **状态图禁手绘**：spec 的状态机图一律由嵌入语义经固定驱动渲染进 `RENDERED` 围栏，禁止手绘。审计器必须在未掩码原文上拒绝围栏外的 `stateDiagram`；`flowchart` 不是状态图，不计入。存量手绘图在下一次行为变更时改为生成，改过的 spec 不得再留手绘状态图。
- **状态图**：标签块之后附一行可见约束（"下列围栏由嵌入语义渲染生成（RENDERED::<name>），禁止手改"）+ `<!-- RENDERED:<name> BEGIN/END -->` 锚点包裹的 ```mermaid 围栏，内容为驱动 render 模式生成的 Mermaid 状态图（可直接渲染，非表格罗列）；禁止手改。
- **嵌入约束**：代码块只含纯声明（类型、迁移表、全局性质函数），无 main、无 stdio、无文件 IO、无格式化。**零字符串字面量**——嵌入代码中不准出现任何字符串常量（渲染/解析/报告的文本全部归固定驱动）。已有嵌入块若必须列出状态×事件全格，禁止 catch-all。不可达格只作非业务占位：效果列表必须是唯一的 `[Unreachable]`；固定驱动不把它写进快照或状态图，迹线命中即 FAIL。`Unreachable` 是驱动保留构造子，不是业务观察。禁止为了补满全格而新增事件。
- **注释要求**：旧代 `SEMANTICS` 嵌入代码的注释只描述代码本身的语义（类型含义、决策 ID 归因、实现代码对应位置、事件触发条件）——不写对读者说的话（"本代码块是……"由工具处理、"注意……"属于散文），不重复 spec 散文已有的叙述。
- **标签完整性门**：每个 state/event 必须有标签，标签/说明不得引用不存在的名字——缺失或悬空即驱动报错、屏障变红（机械门）。
- **评审门（AI 可辅助的验收判定环节）**：设计图、嵌入语义与标签的**正确性**无法机械判定，由人工或 AI 辅助评审。AI 可协助编写正文；在验收判定中只产出供人核对的评审材料，不进入确定性执行路径：评审者留下记录（`reviews/<name>.review.md`，含图/语义/标签哈希），门只做确定性校验——留档存在、哈希与当前设计图/语义/标签一致、无未闭环 `BLOCKING:` 项。设计图、语义或标签一经变更，哈希变化即强制重新评审；工具不能判断评审结论本身是否正确。
- **不变式纪律**：只写 spec 条款中确实存在、需要跨状态验证的性质（全局/时态性质，如可达性、无循环）。复述迁移表的规则不写——单一来源原则，不多维护第二份表达。

## Workflow

### 1. 新建 core spec

1. 先做 scope check：符合 When to Use 判据才继续，否则退化为普通设计文档。
2. 创建 `docs/specs/<name>/`，把本技能 `templates/` 下全部文件复制到对应位置；新建 spec 必须使用模板工具，不允许另起一套全局脚本。
3. **先写 `### 1.0 设计图景`**。图没有写完，不写 REQ，不写决策编号，不写嵌入状态机，不写 manifest 短语。
4. 图上会分叉的步骤，再写成 REQ 和少数决策。manifest 只锁定图上已经使用的术语，不先于图规定正文必须出现哪些短语。
5. 状态为 `draft` 时允许测试锚点/屏障尚未落地；切到 `authoritative` 前，锚点必须真实存在且 `barriers.py` 全绿。
6. 跑 `python tools/test_audit_spec.py` 与 `python tools/audit_spec.py`，必须 PASS。
7. 交付实施时使用 superpowers:writing-plans，plan 头部的 `Spec:` 必须写清 spec 路径；提交说明与签名遵循仓库 AGENTS.md 约定。

### 2. 变更权威规格（spec-first 变更）

1. 行为变更先改 `### 1.0 设计图景` 上的那一步，再改投影。决策编号记录图上已经定下的取舍，不代替图。
2. 状态机只投影图上会走到的路径。禁止为了穷尽匹配、快照或评审哈希，增加图上没有的事件。已有嵌入块必须全格列出时，不可达格仅为非业务占位，注释不可达并验证驱动不接受为合法业务后继。禁止绕过设计图直接改嵌入代码或散文。
3. 被取代条款**原地合并或删除**，禁止“（已被 Dxx 取代）”之类的补丁标记。
4. 同步 `tools/audit_manifest.json`（term、锚点、契约、决策范围）；**移动或删除章节时必须同步修正所有引用该章节的 occurrence/scoped 规则**，审计器不得保留悬空规则。
5. 依次跑 `test_audit_spec.py`、`audit_spec.py`、`barriers.py`。spec 领先代码时（行为变更先改 spec、代码尚未实现）：`spec_status` 保持 `draft`，`code_contracts`/`test_anchors` 指向目标实现、暂未命中时审计降级为 warning，不阻断；代码实现落地、契约/锚点/屏障真实命中且 `barriers.py` 全绿后，再与代码同批提交并切 `authoritative`。
6. plan 与 spec 冲突时，**未推翻的目标行为**以 spec 为准，改 plan。若执行中发现 spec 假设不成立（见「自省」），停手告知用户，不得为迁就条款而改 plan/代码一条路走到黑；用户确认后再归因决策 ID 并改 spec。

### 3. 审计 core spec

审计先回答：设计图是否能从入口走到结果，失败后继是否只有一个。审计器 PASS 不回答这个问题。结论必须还有可复现证据和分级问题清单：

- 以 `reference/quality-gates.md` 十门为框架逐项打分；
- 对每条 P0/P1 问题给出 spec 行号、代码/测试证据、修复动作；
- 审计结束时必须实际运行 `audit_spec.py`、`test_audit_spec.py`、`barriers.py`，把真实输出写进结论。
- 审计器 PASS 不能覆盖身份/分层/What-How 混写。发现这类问题按「自省」告知用户，不要输出「照条款改代码」当作唯一整改。

### 4. 存量 spec 迁移

存量权威 spec 迁入 core-spec 布局时：

1. 先保留正文既有章节编号与交叉引用，不要为套模板做大规模重排；把迁移前版本冻结到 `history/YYYY-MM-DD-<标题>.md`。
2. 把实施波次、迁移步骤与设计推进内容移入 `plans/` 或 roadmap，正文只留规范性摘要与指针。
3. **保留已通过验证的既有工具**，将其迁入 spec 自带 `tools/` 并改为 canonical 文件名（audit_spec.py / audit_manifest.json / barriers.py 等）；只适配路径常量，不得为了统一把成熟工具替换成模板实现。
4. 同步 `audit_manifest.json`：移动章节后，相关 occurrence/scoped 规则要么指向新章节，要么收缩为对正文摘要/决策记录的检查。
5. 更新仓库内引用（AGENTS.md、发布文档、未冻结的 active plan）；`history/` 与历史 plans 中的旧路径不改写。
6. 新位置全套验证 PASS 后，才删除旧全局脚本；spec、tools 与代码同批提交。

### 5. 记录与关闭 issue

1. 发现 spec 与代码/线上行为不一致、或风险待确认且暂不改行为时，在 `issues/` 按 `issues/README.md` 骨架登记，状态 `open`。
2. §9 决策日志新增或归因决策 ID 并落地后，原地将 issue 改为 `resolved` 或 `wontfix`，填写关联决策 ID；不迁入 `history/`。
3. 变更或审计前先打开 `issues/`，确认 open 项是否影响本次变更；有影响的必须先完成 §9 决策归因，再进入 plan/代码。

## Hard Gates（不满足即失败）

| 门 | 判据（摘要） |
|---|---|
| G0 设计图 | `### 1.0 设计图景` 从入口到终点；动作节点有谁、对象、动作及实际可达分支的观察和后继；终点不虚构分支 |
| G1 精确与可追溯 | 无模糊词；图上分叉写成的需求有唯一 REQ ID。不为过门补需求 |
| G2 异常与 NFR 完整 | 状态机覆盖失败分支；NFR 全部量化；错误模型完整 |
| G3 内部一致 | 一个术语一个定义；被取代条款已合并/删除；图、表、验收不互相矛盾；正文无实施波次标识与实现级设计 |
| G4 验证实测全绿 | 审计器、负例自测、屏障命令实际运行并通过；测试锚点真实存在 |
| G5 治理与元信息 | 每条规范可归因决策 ID；版本/受众/范围/术语表/Out of Scope 完整 |
| G6 外部输入 | 只闭合设计图上会到达的输入。不写图上不会走到的笛卡尔积 |
| G7 内嵌语义 | 嵌入块是设计图的投影。全格只为编译器。性质门 PASS 不证明标签和迁移一致 |
| G8 语义一致性检查（spec↔实现） | 收尾时由独立 reviewer 对照现行 spec、实际代码与测试结果，逐条核对可达路径、错误/取消后继及边界；报告附规格条款、代码位置、测试证据与未闭环 BLOCKING。G8 不要求新增专用运行记录、rawfacts/trace 协议、语料提交或重放系统；评审不能替代实际测试 |
| G9 评审门（AI 可辅助） | 标签完整性；评审留档的设计图/语义/标签哈希新鲜、无未闭环 BLOCKING；人工逐事件核对可达迁移 |

完整检查表见 `reference/quality-gates.md`。新建或本次发生行为变更的 spec 有门不满足，不得以本次升级宣布 authoritative；未触及行为的存量 spec 缺 G0 时登记迁移债务，不仅凭新门追溯改写既有状态。结构审计器 PASS 不等于十门全绿。

## Common Mistakes

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 审计器 PASS 就宣布 spec 正确 | 词法检查发现不了语义矛盾和契约漂移 | G3 自检 + 逐条契约对照代码 + 屏障实跑 |
| 保留旧条款并标注“已取代” | 一份文档两套语义 | 原地合并或删除，历史交给 git 和 history/ |
| 只改一处，不同步目标/状态表/验收 | 开发按旧语义实现 | 变更时全文检索相关章节一并收敛 |
| spec 里写测试锚点但不跑 | 锚点可能根本不存在 | 锚点列入 manifest，audit 校验存在性，barriers 实跑 |
| 把锁算法、实施波次写进 spec 主体 | 文档臃肿、What/How 不分 | 下沉到设计文档/plan；spec 只保留契约性约束 |
| 迁移时把成熟验证工具替换成模板 | 丢失已固化的规则与负例 | 存量迁移保留既有工具，只改 canonical 文件名与路径 |
| 移动章节后不更新 manifest | 审计规则悬空或错指章节 | 同步修正 occurrence/scoped 的 sections 与 count |
| 把问题调查过程直接写进 spec 正文 | 正文混入非规范性内容，行为无法判定 | 调查记录进 `issues/`，正文只保留决策 ID 归因结论 |
| spec 写成现状快照（记录当前代码行为） | 目标行为被现状锁死，无法驱动变更 | spec 定义目标，代码实现目标；现状与目标不一致是待变更信号，不是 spec 写错 |
| spec 凭空定义代码事实（错误码/常量/签名） | 契约与代码漂移，屏障形同虚设 | 代码事实引用必须 grep 到代码，列入 manifest code_contracts |
| 发现 spec 写错仍按条款把代码/manifest 改到位 | 错误假设被 audit 锁死，越做越难撤 | 停手告知用户，商量改 spec；确认前不扩大改动面 |
| 把「spec 是权威」读成「出错的 spec 不准改」 | 执行者不敢质疑，一条路走到黑 | 权威只约束已确认的目标行为；假设被推翻就改 spec |
| 为了穷尽匹配补事件，图上没有这条路径 | 门绿了，实现者不知道发哪个事件 | 删事件。不可达格只作非业务占位，不当作合法后继 |
| 评审写「无阻断项」，但没有逐项核对标签与迁移效果 | 人工结论无依据，门仍可能通过 | 按事件核对。效果对不上就写 BLOCKING |
| 用短语出现次数逼正文 | 模型补句子去满足计数，设计不变 | 短语规则指不回图上的一步就删 |
| 手写摘要代替设计图 | 摘要和后继各说各的 | 设计图是正文。嵌入块只投影图 |

## Red Flags — STOP and fix

- 看到“可能 / 大概 / 尽量 / 友好 / 快速”等词出现在规范性条款里
- “（已被 Dxx 取代）”“本次暂不处理”出现在权威规格正文
- `grep` 不到 spec 引用的测试名
- 变更没有归因决策 ID 就想改代码
- 状态机变更绕过嵌入语义直接改散文或代码
- spec.md 内嵌代码块 diff 红、不变式 FAIL，仍继续提交
- 实施波次标识或“第 N 波次实施”出现在权威规格正文
- spec 正文出现"当前实现是 X""现有代码为 X"等现状描述，而非目标定义
- 拿错误条款压过身份/分层判断，不告知用户就继续实施
- 为了 audit 变绿，把已知错误的目录/身份写进更多契约
- 为了性质门、快照或评审哈希，增加图上没有的事件或短语
- 两个事件标签相同，或标签描述的效果在会走到的迁移里不存在
- 审计器 PASS 之后宣布设计完成

以上任何一条出现：先停、先告知用户。确认修 spec 则先修 spec 再继续；确认不改则记录 issue，不得假装条款有效并继续铺开。
