## § 决策图 emit 通道

**唯一合法 emit 通道是 `ask` 工具（带 `questions[]` 参数）**。

```typescript
ask({
  questions: [
    {
      id: "q1_id",
      header: "≤12 字标题",
      question: "完整问题描述",
      options: [
        {label: "推荐项", description: "依据 + 简要说明", preview: "（代码/UI/链接预览）"},
        {label: "另一可选项", description: "..."},
        ...
      ],
      multi: false
    },
    ...
  ]
})
```

字段：

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | 是 | 决策点唯一 ID（用户回话时通过 id 引用） |
| `header` | 是 | 决策点 ≤12 字短标题（界面 chip） |
| `question` | 是 | 完整问题描述（用户视角） |
| `options[]` | 是 | 选项数组，每项 `{label, description, preview?}` |
| `options[].label` | 是 | 选项短标题（≤6 字最佳） |
| `options[].description` | 是 | 选项说明（含依据 / 为什么是忌讳） |
| `options[].preview` | 否 | 代码片段 / UI 示意 / 外部链接 |
| `multi` | 否 | 是否多选；默认 false（单选） |

**为什么不能用 markdown 列表替代**：

| 问题 | 后果 |
|---|---|
| markdown 列表不支持点选 | 用户必须回"Q1 选 A"，违背 1-2 字回话原则 |
| markdown 列表无必拍板（`🛑`）UI 渲染 | "agent 不替用户拍"语义丢失 |
| markdown 列表无单/多选区分 | 用户无法表达"两个都要"或"都不" |
| markdown 列表无法承载"已定 vs 待定"区分 | 用户认知过载，无法识别哪些是真决策 |
| markdown 决策图当"汇报工具"用 | 决策图本质（等你拍板）被偷换为"agent 讲解方案" |

**示例**：若 agent 在普通文本中列出多条待决问题，用户需要逐条理解并自行组织回复；交互式工具可将选项分开呈现，降低回复成本。

## § 决策图

> ⚠️ **本节是概念骨架**——便于人类审阅 ask 工具的实际 emit 形态。**实际 emit 必须经 `ask` 工具**（见 § 决策图 emit 通道），不得直接写下面这段 markdown 到对话流。
>
> **回退路径**：若 ask 工具调用被禁用（极少数脚本场景），按 SKILL.md § HARD-RULE 在文本里贴"决策图 JSON"让用户审阅，**不要**贴本节 markdown 骨架。

### 决策图双栏形态（反例 + 推荐）

ask 工具的核心用法是**列出对照**：先给 agent 推荐的若干方案 + agent 推测用户**不希望**的反例/忌讳，使用户能反向剔除或正向认可。每条决策点的输出格式：

```markdown
#### Q{N} - {问题标题}
{问题正文}

推荐（***）：
1. {推荐项 1} —— {依据}
2. {推荐项 2} —— {依据}
3. {推荐项 3} —— {依据}
...
n. {推荐项 n}

不希望（忌讳）：
{n+1}. {忌讳 1} —— {为什么这是忌讳}
{n+2}. {忌讳 2} —— {为什么这是忌讳}
...
k. {忌讳 k}
```

要点：

- **推荐项标记为 `***`**：这是 agent 强推的项
- **不希望**列出的是 agent 推测的忌讳/反例，**双方数量不固定**（agent 推测用户有几个忌讳就列几个）
- 用户的"不指定"行为 = 默认走 `***` 推荐项

### 完整结构

```markdown
## 决策图：{任务名}

扫描到 N 个决策点（最多 8；超出见 § 超限处理）。

### 必拍板

#### Q1 - {问题标题}
{问题正文}

推荐（***）：
1. {推荐项 1} —— {依据}
2. {推荐项 2} —— {依据}

不希望：
3. {忌讳 1} —— {为什么忌讳}
4. {忌讳 2} —— {为什么忌讳}

#### Q2 - {标题}
...

### 探路（agent 推测的不希望项，仅需纠正不对的）

- 我猜你不要的是：{一句话}（依据：{仓库惯例 / spec}）
- 我猜你不要的是：{一句话}（依据：{路径成本}）
- ...

### 子任务拆分建议（如 N > 8）

- 子任务 1：{范围}，决策点 {N1} 条
- 子任务 2：{范围}，决策点 {N2} 条
- 跨子任务依赖：{X 必须在 Y 之后}

---

可用回话（1-2 字）：
- **够了 / go** → 进入免打扰
- **我没看懂** → 拆词解释
- **重说** → 重新生成决策图
- **加进去 X** → 补决策点
- **改问题** → 重新扫描
- **拆** → 拆子任务
- **暂停** → 立即停手
```

### 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 任务名 | 必填 | 简述任务目标 |
| N | 必填 | 决策点总数 |
| 必拍板 N 条 | 必填 | 每条 Q 独立，含推荐 + 不希望双栏 |
| 探路 | 选填 | agent 主动推测的不希望项 |
| 子任务拆分 | N>8 时必填 | 见 § 超限 |
| 快捷项 | 必填 | 至少给一句"如需 X，回 Z" |

## § 必拍板 vs 探路判据

agent 划分决策点的依据：

| 判据 | 必拍板 | 探路 |
|---|---|---|
| 可逆性 | 不可逆（删文件、改 schema、提交） | 可回滚 |
| 影响面 | 跨模块 / 跨任务 | 单模块 / 单步 |
| 默认合理性 | 无合理默认 | 有合理默认 |
| 推项信心 | agent 信心低（< ⭐⭐⭐） | agent 信心高（≥ ⭐⭐⭐） |
| 用户敏感性 | 用户已说过"这个必须我决定" | 用户未表态 |

例：

- "用 SQLite 还是 Postgres" → 必拍板（影响面大）
- "端口用 8000 还是 8080" → 探路（agent 推 8000，信心 ⭐⭐⭐⭐）
- "处理后是否保留队列顺序" → 必拍板（可能影响后续任务处理）
- "是否在 commit message 里加 emoji" → 探路（agent 推不加）

## § 推荐指数

agent 给出 1-5 星：

- ⭐⭐⭐⭐⭐：agent 极高（仓库惯例 / 用户已说过 / spec 已规定）
- ⭐⭐⭐⭐：agent 高（行业惯例 / 项目惯例）
- ⭐⭐⭐：agent 中（多个合理选项但某项显著胜出）
- ⭐⭐：agent 低（多个合理选项持平）
- ⭐：agent 极低（agent 没有强意见；用户必须回）

注：推荐指数是 agent 自检结果，可填可不填（用户说"去掉"则去掉）。

## § 探路格式

agent 一句话推用户**不想要**的项：

```markdown
- 我猜用户不想要的是 **{X}**，因为 {依据}（推荐指数 ⭐⭐⭐⭐）
```

用户回应方式：

- "对" → 走默认（不引入 X）
- "X 我要" → 改之（X 升格为推荐项）
- "X 待定" → 升格为必拍板

## § 免打扰触发条件

agent 在免打扰期间（用户已确认"够了"）回来问的唯一标准：

### 必须问

1. **不可逆操作**：删文件（rm -rf）、删数据库记录、改 schema、生产部署、提交
2. **问题太大**：影响 3+ 步后续 / 改动跨模块 / 一旦走错回滚 > 1 小时
3. **用户显式标记 `🛑`**：用户拍板时标了 `🛑 必须拍板`，agent 不替决定
4. **新发现的事实与原决策冲突**：发现的事实让原选项无效

### 可不问（agent 自己选 + 任务后汇报）

1. 中间变量的命名 / 顺序
2. 错误处理策略（除非跨模块）
3. 日志格式 / 调试信息
4. 临时文件清理
5. 注释风格

### 安全选项判据

agent 选"不问"时，选的选项必须满足：

1. **可回滚**：git revert / 删文件恢复 / 重跑
2. **低破坏**：不影响线上 / 不破坏数据
3. **可预测**：按现有 spec / 仓库惯例延伸
4. **失败兜底**：出错时有 fallback 路径

## § 超限处理

### 触发条件

N > 8 条独立决策点。

### agent 行为

1. agent **主动**提示"拆子任务"，**不等用户问**
2. 给出拆法（按依赖 / 按模块 / 按阶段拆）
3. 等用户回 "拆" / "go 子任务 1" / "调整拆法"
4. 用户回 "拆" 或 "go 子任务 N" → 开始子任务 N 的决策图
5. 子任务访谈在原任务线程继续，不另起会话

### 拆法判据

- 按依赖拆：A 必须在 B 之前，A 先访谈
- 按模块拆：模块 A 路径边界独立，先访谈 A
- 按阶段拆：调研 → 设计 → 实施 → 测试

### 不允许

- N = 15 还强行摆 15 条（用户认知过载）
- 用户没回就自己开始子任务 1（违反"用户拍板"前提）

## § 任务后汇报

任务完成后 agent 输出（**省略即违规**）：

```markdown
## [ask] 任务完成：{任务名}

**用户拍板**：{N1} 项
- Q1 选 A
- Q2 选 B

**Agent 自行决定**（免打扰期间，可回滚）：
- 决策 X：选了 A，因为 {依据}。回滚：{命令}
- 决策 Y：选了 B，因为 {依据}。回滚：{命令}
- ...

**未触发项**：{原决策图中标了"探路"且用户未纠正的项，自动走默认}

**完成度**：{完成 / 部分完成 / 中止}（{原因}）
```

## § preview 何时用

- 选项涉及代码片段差异：贴 5-15 行代码对比
- 选项涉及 UI 视觉差异：贴布局示意
- 选项涉及外部资源：贴参考链接

不贴：

- 长篇背景说明（应放决策点正文）
- 与选项无关的实现细节
- 全量算法（如决策树）

## § 零决策点声明

用户回"别问了，开干"或决策图上限为 0 时，输出此声明替代决策图。

格式（1-3 行）：

```markdown
[ask] 零决策点声明
- 任务：{任务名}
- 跳过原因：{用户说"开干" / 任务极简}
- agent 自决项：{清单 of agent 自行决策的范围}
```

作用：

- 不让用户问"为什么没列决策点"
- 让用户看到 agent 即将自决的范围（透明）
- 与任务后汇报衔接

## § 用户反馈快捷项

ask 在任何阶段都要主动列出可用快捷项，让用户回话简短（理想 1-2 字）。

### 决策图给齐后必须附加的快捷项提示

agent 出完决策图，**必须**附：

```markdown
可用回话：
- "够了" / "go" → 进入免打扰
- "我没看懂" → 拆词解释
- "重说" → 重新生成决策图
- "加进去 X" / "你漏了 X" → 补决策点
- "改问题" → 重新扫描
- "拆" / "并行走" → 拆子任务
```

不必每条都展开解释，按需展开。

### 各阶段快捷项适用性

| 阶段 | 适用快捷项 |
|---|---|
| 决策图给齐前（agent 还在生成） | "暂停" / "改问题" |
| 用户拍板中（回 "A" / "B"） | "重说" / "加进去" / "我没看懂" |
| 决策图已给齐，等用户拍板 | "够了" / "加进去" / "跳过 X" / "拆" |
| 免打扰执行中 | "暂停" / "加我刚说的" / "拆子任务走并行" |
| 任务后汇报后 | "我没看懂" / "重说汇报" / "回滚 X" |

agent 在每个阶段输出时，**自动选当阶段最相关的 3-5 个快捷项**附加在末尾。

### "我没看懂"的拆词解释策略

agent 收到"我没看懂"后：

1. 定位"看不懂"的部分（是某决策点？某选项？某推荐？还是整体？）
2. 把该部分用更短的话 + 具体例子重说
3. 不重新生成决策图本身
4. 重说后再次询问："现在看懂了吗？或要重说整张决策图？"

### "加进去" / "你漏了 X"的处理

agent 收到"加 X"后：

1. 把 X 加入决策图
2. 按 § 必拍板 vs 探路判据 自动归类（用户可纠正分类）
3. 重生成决策图，X 进入新位置
4. 不删除原图其他项

### "改问题"的处理

agent 收到"改问题"后：

1. 重新扫描任务路径
2. 重生成完整决策图（旧图覆盖，不保留）
3. 询问"这次对了吗？"
