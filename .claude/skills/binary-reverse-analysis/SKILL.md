# 二进制逆向分析

## 概述

逆向最大的失败模式是**假设未验证就当事实**。验证优先于结论。

权威依据：
- "Validation is the most critical and most skipped stage"——逆向失败根源
- "IDA F.L.I.R.T. 认为 false positive 比 false negative 更糟"——假阳性比漏报更危险

## 何时使用 / 何时不该用

**用**：二进制分析、Ghidra/IDA 反编译、签名/模式搜索、调用约定推断、内存/磁盘补丁、vtable/RTTI、跨架构对齐

**不用**：
- 纯源码级调试 → 走 `superpowers:systematic-debugging`
- 只是"卡住想放弃" → 暂停并重新检查证据、假设和下一步可验证动作

## 逆向铁律

1. **有疑惑先 web search，后问用户/后猜**
   - 调用约定、API 行为、工具误判、补丁术语 → 先搜权威
   - 反例：假设 x64 的 `dl` 寄存器惯用语可移植到 i386 thiscall（i386 走栈）

2. **有假设必运行时验证**
   - 静态（Ghidra/IDA）假设 → 进程内存/调试器验证 → 修正
   - 禁止停在静态分析就下结论
   - 反例：Ghidra 会把 thiscall 误判为 cdecl（工具不可全信）

3. **逆向核心是大量测试、小点击破**
   - **禁止**"停下来要求用户手动测试"。你自己有调试器/ReadProcessMemory/Python attach
   - 每个假设设计最小验证实验，自己跑

4. **呈现接地气**
   - 给"成功/失败 + 下一步可操作结论"，不抛裸 RVA/偏移/签名字节让用户把握不了
   - 反例：只报告"toggle 函数 RVA=<地址>"而不说"这意味着什么、下一步验证什么"

5. **理解用户旨意——区分语义层级**
   - 用户用宽泛词（"补丁""hook"）时，先区分具体类型再动手
   - 反例：用户说"不要加磁盘补丁"→ 误以为也不要内存补丁，撤销了正确的工作
   - 不懂先 web search 或先问，不要自作主张

## 早停信号识别

早停信号分两类：**外部信号**（环境反馈）和 **内部信号**（自己的念头）。
出现任一类，停，质疑核心假设，不在同一层面反复微调。

### 外部信号（环境反馈）

| 信号 | 该质疑的核心假设 | 错误反应（原地打转） |
|------|----------------|-------------------|
| 签名/模式匹配数爆炸（如数百+） | 签名太宽 / 调用约定错 / 惯用语不可移植 | 换参数微调签名，继续搜 |
| 预期对象在内存中找不到 | 对象生命周期（瞬态？）/ 搜索方式（漏 vtable？）/ 时机 | 加大搜索范围、重试循环 |
| 同一思路失败 ≥3 次 | 整个方向错（架构/约定/对象模型） | 第 4 次换参数 |
| "可能是 X" 浮现 | 没验证 = 猜 | 直接当结论写代码 |

通用规则：**匹配数异常（爆炸或为零）= 假设出问题的强信号**。
宁可零匹配重新设计签名，不要淹没在假阳性里。

### 内部信号（自我合理化检测）

当浮现以下念头，停——这是在合理化逃避验证，不是在做判断：

| 浮现的念头 | 现实 | 正确做法 |
|-----------|------|---------|
| "用户可能只是随口感叹/不重要" | 在绕过"先确认"，把不确定的指令当噪音 | 当作正式指令，先确认再行动 |
| "这个应该够明显了，不用问" | 在跳过流程初期的询问 | 流程初期必须问，禁止不问就决策 |
| "直接呈现方案，用户边看边改" | 在跳过 user review gate | 先问关键决策，获批再呈现 |
| "签名大概对，先试试看" | 没验证 = 猜 | Ghidra 反编译确认调用约定再写签名 |
| "对象应该在内存里，再搜大点范围" | 在同层反复，没质疑对象生命周期 | 停，质疑对象是否瞬态 |
| "可能是 X，先按 X 写" | 把假设当结论 | 先做最小验证实验 |
| "让用户手动测试一下吧" | 在甩锅，逆向核心是你自己测 | 自己 attach/调试 |
| "这个 RVA/偏移用户应该能看懂" | 呈现抽离，用户难把握 | 给结论 + 下一步，不抛裸地址 |

核心识别法：**念头的内容是"省略验证"或"绕过询问"，就是合理化**。
逆向的护城河是验证密度，任何降低验证密度的念头都该被这个表拦下。

## 方法论

### 静态→动态→修正 循环

```
静态分析（Ghidra/IDA 反编译）
    ↓ 形成假设（调用约定/对象布局/函数语义）
动态验证（调试器/ReadProcessMemory/Python attach）
    ↓ 证实或证伪
修正假设 → 回到静态
```

**不停在静态就下结论**。逆向结论的置信度 = 动态验证过的次数。

### 跨架构功能对齐

有参考实现（如 x64 已工作）时，目标架构逐项对齐清单：
- [ ] 每个步骤是否都有对应实现？
- [ ] 参数传递是否等价？（x64 寄存器 vs x86 栈 vs ARM 寄存器）
- [ ] 对象布局是否对应？（vtable 偏移、成员偏移、多继承 sub-object）
- [ ] 补丁类型是否一致？

### 补丁类型决策树

详见 `patch-types.md`。

```
目标对象/行为持久存在？
├─ 是 → runtime 操作（读写字段、调函数）
└─ 否（瞬态/创建时决定）→ 改代码路径
    ├─ 需要永久 → coldpatch（磁盘补丁，改二进制）
    └─ 只需运行时 → hotpatch（内存补丁，改进程代码段）
```

## 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 假设调用约定可移植 | 签名假阳性爆炸 / 参数读错 | 查 `calling-conventions.md`，Ghidra 反编译目标函数确认 |
| 只用 primary vtable 搜 C++ 对象 | 多继承对象漏掉 | 枚举所有 vtable（RTTI complete object locator） |
| 瞬态对象用 runtime-only 方案 | 注定找不到对象 | 改代码路径（hotpatch 调用点） |
| 磁盘/内存补丁语义混淆 | 撤销正确工作 / 惹怒用户 | 查 `patch-types.md`，先确认用户旨意 |
| 静态分析下结论 | 假设当事实 | 必须动态验证 |
