# clearExplan

先判断场景，再选图。禁止把「改哪些文件」的计划树套到「这段代码现在怎么跑」上。

**进度不在本技能：** 用户问「跑到哪了」→ 读 `progress.md` 和 plan checkbox。

## 场景（第一步，必须选一个）

| 场景 | 用户在问什么 | 典型说法 |
|---|---|---|
| A 计划图景 | 准备改什么、改完长什么样、计划怎么来的 | 「设计是什么」「模块规划」「按审查准备怎么改」「来龙去脉」 |
| B 技术细节 | 仓库里一个符号现在怎么被调用、何时发生、对端收到什么 | 「X 是谁发的」「什么时候发」「是发给前端/客户端吗」「通过什么发的」 |

混合提问：先 B（把机制讲清），用户要改动图景再 A。不要两套图搅在一段里。

**不要用本技能：** 未主动要求结构/机制时；往 plan 文件里自动插图；单一文件机械改动。

~~旧规则「已经在讨论实现细节就不要给概览」作废。~~ 实现细节走场景 B，必须给调用树。

## 反抽象（两场景共用）

用户懂技术、不懂本仓库。禁止自造词、比喻、门牌/销户之类。函数名可保留。纯 ASCII 树（`├──` `│` `└──`），不用 Mermaid/emoji。

具体不是写得更长。每个节点或要点在写下之前先问三句，有一句否就不写：

1. 这是用户要的吗
2. 看不到这一点，会不会判错
3. 这一点帮不帮用户把握项目

节点正文必须是可观察动作，不查规格也能读完。要写出：谁、对哪个对象、做什么、成功看见什么、失败看见什么。阶段号、级别、层号不能单独当节点。规格里的「第 2 步」只能放在动作后面的括号里，括号前的句子必须已经说完。

坏：`处理失败（第 2 步）`。遮住「第 2 步」后，读者指不出调用方、目标对象、动作、成功和失败各看见什么。它的子节点如果还在用这个编号，先补本节点，再写子节点。

好：`任务调度器读取待处理队列中的下一项；读取成功时交给执行器，队列为空或读取失败时记录对应结果（规格把读取称为第 2 步）`。

不要只写阶段名或概念标签。首次出现时说明实际动作：谁对哪个对象做什么，以及成功或失败后可观察到什么。领域术语可以保留；若影响理解，再结合上下文解释。

## 场景 A — 计划图景

决策者 30 秒要看到：改哪些文件、关键路径旧/新、多端怎么对应、放弃了什么。不要写测试命令（那是 plan 正文）。

默认出图 1 + 图 2；多端再出图 3；问「怎么来的」再出图 4。图前一句说明这张图回答什么。

**图 1 文件规划：** 每个文件一行职责。`← 新建（…）` / `← 修改（…）`。变更点标 `旧:` `新:`。

**图 1b 提交级全景：** 回答「这几个提交都改了什么」。仅当交付跨越多个提交或多个仓库时出；单仓库单批次不用（那是图 1 的职责）。规则：顶层按仓库分组 → 每个提交一行（7 位短 SHA + 一句话类别与内容，如「核心行为变更」「测试收口」）→ 提交下缩进列文件（沿用图 1 的每文件一行职责与 `旧:` `新:` 标注）。禁止把未提交的工作区内容画进本图——只画已存在的提交。

**图 2 调用链：** 从入口到结果，只画关键路径，标旧/新为什么旧的不行。

**图 3 对称表：** 仅多端/多模块。对齐项逐行，差异单独一段。

**图 4 来龙去脉：** 按日期写发生了什么、决定了什么。不写规格决策 ID。列出放弃的方案和原因。

禁止：把计划树里的「新建包」编造出来（仓库里没有的目录不要画进去）。

## 场景 B — 技术细节

先读代码再说话。禁止凭记忆编「发给前端/发给客户端」。

回答顺序固定；简短追问只答相关消息，不重复整套流程：

1. **先写参与对象和方向。** 跨端流程先列清独立进程，例如「管理界面」「任务服务」「执行器」。单条消息开头直接写「发送方 → 接收方：消息名」。角色名称要能区分发送方与接收方。
2. **说明实际动作（有代码依据）。** 谁调用（文件及函数）；经哪条 WebSocket/HTTP，或只是进程内调用；接收方实际收到什么、接着做什么。代码位置可放图后，不能让函数名遮住发送方向。
3. **一张时序调用树。** 从真实入口画到出口，按发生顺序编号。每个网络消息节点独立写「发送方 → 接收方：消息名，关键载荷及作用」；本地采集、编码、解码、绘制写「对象内部：动作」。不能只靠缩进、上一节点主语或箭头图例猜方向。
4. **用户正在比较新旧实现时写清边界。** 该消息是既有还是本次新增；在哪一段连接使用；是否转发给其他执行方；旧实现实际收到的消息是否改变。消息仅由服务端消费就明确写「服务端处理，不转发」。

能力、READY 及确认类字段必须补齐三个信息：
- **主体：** 谁的能力或状态。例如管理界面的本地解析能力，不是任务执行器的能力。
- **观测：** 实际检查了什么。例如只检查解析功能存在，不代表具体格式支持、处理完成或结果已显示。
- **用途：** 谁依据此值做什么；是提示、选择协议还是阻止后续启动。名字含 READY 不能当作已经做完准备工作的证据。

输出示例（合成流程；以下消息名、字段和流程均为虚构说明，不代表任何真实产品协议或约束）：
```text
管理界面 → 任务服务：PARSER_AVAILABLE {available:true}
└── 任务服务内部：记录管理界面报告的本地解析功能是否存在
    └── 不转发 PARSER_AVAILABLE 给执行器；随后由任务服务单独创建任务
```

用户指出对象或方向理解反了时，第一句先纠正「不是A→B，是C→D」，再给最短消息树；不要先解释字段、用途或设计理由。

场景 B **禁止：**

- 出图 1「文件规划（新建/修改）」——那是计划，不是现状
- 比喻
- 先讲四个假设场景再讲定义
- 未 grep/read 就回答「发给谁」

界面若最终能「看见」结果，必须写清中间层：领域事件 → 哪个订阅者 → 哪个投影 → 哪条 channel topic。不要把内部命令说成前端协议。

## Common Mistakes

| 错误 | 后果 | 正确 |
|---|---|---|
| 用场景 A 的改文件树回答「X 是什么」 | 用户以为在听现状，实际在听还没做的计划 | 先三句 + 现状调用树 |
| 未读代码就猜发给前端/客户端 | 把进程内命令说成协议 | grep 调用点后再说 |
| 内部操作和状态事件混谈 | 以为会向另一进程发送消息 | 分开：谁发、是不是消息 |
| 比喻（门牌、销户） | 越听越乱 | 用符号名和可观察动作 |
| 节点只有阶段名或术语标签 | 读者无法判断实际动作 | 写清执行方、对象、动作及结果 |
| 实现细节不画树 | 只剩散文，关系理不清 | 场景 B 必须有调用树 |
| 计划树里出现仓库没有的包 | 决策者按幻觉目录想问题 | 只画真实路径 |
| 把「实现细节不给概览」当成可以不画树 | 技术问题用散文敷衍 | 细节走场景 B |
| 参与方简称相同或角色不清 | 用户把消息接收方认反 | 先列独立进程，每条消息完整标明发送方→接收方 |
| 只说能力上报，不说是谁的能力及服务端是否转发 | 把界面能力误认成执行器能力 | 写明主体、实际观测、用途和转发边界 |
