分析当前暂存变更，生成符合 conventional commits 规范的中文提交消息；本地存在可用 GPG 签名私钥时，通过 ask 让用户选择是否签名，再执行提交。

## 执行步骤

1. 检查暂存文件：
   ```bash
   git diff --staged --name-status
   ```
2. 查看暂存差异：
   ```bash
   git diff --staged
   ```
3. 若暂存区为空，停止，不创建空提交。
4. 生成提交消息：
   ```text
   <type>: <简短中文描述>

   - <变更详情1>
   - <变更详情2>
   ```
5. 用户未明确要求执行提交时，生成消息后停止，不检查密钥、不提交。已获提交授权且暂存区非空时，再检查本地 GPG 签名能力：
   ```bash
   command -v gpg
   gpg --list-secret-keys --with-colons --fingerprint
   ```
   只把具备签名能力、未过期、未撤销、未禁用且有可访问私钥材料的密钥列为候选；只有公钥不算。列出候选不等于已解锁，不为探测而提前试签名或索取口令。
   检测命令失败不等于没有密钥，应报告原因并停止，不自动改为普通提交。缺少 `gpg` 时，先检查 `nix-shell`，再按本机工具规则用 `nix-shell -p gnupg` 临时提供；无法提供时报告阻塞，不全局安装。记录检测所用的 GPG 可执行路径，后续签名使用同一程序与同一 `GNUPGHOME`，不能在临时环境检测后让 Git 调用另一个 GPG。
6. 存在可用候选时，必须调用 ask，提供“GPG 签名提交”和“不签名提交”两个选项，等待用户选择。不得根据 Git 配置、历史选择或主代理偏好自动决定；未回答就不提交。
   - 用户选择签名，且有多个可用密钥时，再通过 ask 让用户选择密钥，展示可区分的公开指纹，不输出私钥或口令。
   - 同一次提交已通过 ask 确认且待提交内容、密钥未变时，不重复询问。
   - 检测成功且没有可用候选时，说明无法使用 GPG，不提供不可执行的签名选项。用户已明确要求签名时停止；未要求签名时按普通提交处理。
7. 按用户本次选择执行：
   ```bash
   # GPG 签名；密钥只用于本次命令，不写入全局配置
   git -c gpg.format=openpgp -c gpg.openpgp.program="<检测所用的GPG可执行路径>" -c user.signingkey="<用户选择的密钥>" commit -S -m "<生成的提交消息>"
   # 明确选择不签名，或没有可用密钥且用户未要求签名
   git commit --no-gpg-sign -m "<生成的提交消息>"
   ```
8. 提交成功后运行 `git log -1 --stat` 展示结果；签名提交使用同一 GPG 程序验签：`git -c gpg.openpgp.program="<检测所用的GPG可执行路径>" verify-commit HEAD`。验证失败时如实报告，不宣称已验证成功。

## 提交类型

- `feat:` 新功能
- `fix:` 修复问题
- `refactor:` 重构且不改变行为
- `docs:` 文档更新
- `test:` 测试变更
- `chore:` 构建、工具或维护变更
- `style:` 仅格式调整

## 硬约束

- 本地存在可用 GPG 签名私钥时，必须通过 ask 取得本次签名选择；不得把 Git 默认配置当作用户选择。
- 不生成、导入或导出私钥，不读取或记录口令，不把个人密钥 ID 写进通用命令，不修改全局签名配置。
- 签名或解锁失败时保留暂存区并报告原因，不能自动降级成无签名提交；不能用 `--no-gpg-sign` 绕过用户的签名选择。
- 提交消息必须使用中文并遵循 conventional commits。
- 提交消息不得包含 AI 标识。
- 只提交暂存区内容，不自动暂存额外文件。
